三大模式之一 - 贯穿大型组织的历程

整合。

内源越来越多地与某个合作职能一同获得资金支持 - 比如 OSPO、开发者体验团队或平台工程团队。

关键要拿捏好的是范围：可以通过合作方获得资金，但职责必须覆盖全公司。它的整个前提，就是服务于每一个团队 - 而不只是出钱的那一个。

第一部分
在那些规模最大的内源历程中，我看到了三个值得点明的模式。第一个是整合。 内源越来越多地依托某个合作职能来获得资金和归属，而不再是一项独立的预算 - 比如 OSPO、开发者体验团队、平台工程组织。它们都是天然的合作伙伴。关键要拿捏好的是范围：牵头的职能往往只为对自身职责有帮助的部分给内源出资，但内源的整个前提是服务于每一个团队。做得好的项目，会通过合作方获得资金，同时让职责始终覆盖全公司。

第二个模式 - 支撑体系胜过热情。让项目能扩展、而不是停滞的，不是自下而上的热情；而是实实在在的支撑体系：统一的工具、贡献指南、治理 - 还有同样重要的管理者和 HR 支持，让贡献真正能算进一个人的职业晋升通道里。 随之而来的挑战是：构建这套支撑体系的头号障碍不再是文化 - 而是时间。第一次，“缺乏时间和资源”以百分之八十四，超过了以百分之七十四紧随其后的文化与孤岛思维。只有约百分之二十二的组织会给员工时间去做贡献，约百分之十五会给予奖励，百分之十四会在晋升时予以考量。人们已经被说服；他们只是没有余力去付诸行动。

第三个挑战 - 投资回报。价值显而易见，投入却不然，很大程度上是因为它难以衡量：不到百分之五十的组织会去衡量内源。 还有一个更深层的原因。成本和回报落在不同的账本上。在时间上：你这个季度投入，回报却是全年一点点渗回来的。在范围上：投入的团队往往不是收获收益的团队。按季度、按团队去核算，内源这笔账永远算不太平 - 所以解法是跨越季度、跨越团队地去奖励并认可贡献。如果你需要严谨的投资回报参考文献，那就是 de Silva 与 Izquierdo 的《Measuring InnerSource Value》。

AI 正如何重塑内源

我在整个社区中观察到的
现在进入我承诺的第二部分 - 在实践中，当 AI 遇上内源，我在整个社区里真实看到的情况。
把话说明白
这个误区

内源之所以存在，是因为代码昂贵。如果 AI 让代码几乎免费 - 那这套论证不就站不住脚了吗？

为何它站不住脚

AI 压低的是能编译通过的代码的成本，而不是正确的代码 - 安全、经过测试、久经打磨 - 的成本。

东西一便宜，产量就上去。重复代码也一样。

第二部分
有一个故事，我们很多人都在对自己讲，在反驳它之前，我想先把它直接说出来。内源之所以存在，是因为写代码曾经很昂贵。如果两个团队需要同样的东西，让一个团队构建、另一个团队复用，会更省。这就是它的整个前提：不要重复，因为重复代价高昂。 如今 AI 几秒钟就能写出代码。于是这个误区说：如果创造代码基本免费，那我们不再重复又能省下什么？AI 难道不是悄悄地终结了内源的理由吗？ 这里就是它错在哪里。AI 压低的是写出能编译、看起来没问题的代码的成本。它丝毫 - 一丝一毫 - 都没有改变真正正确的代码的成本：可用、安全、针对你的组织早已吃过苦头才学到的每一个边界情况做过测试。而当你把某样东西变便宜，你就会得到更多。这也包括重复。这个误区把“写起来便宜”误当成了彻头彻尾的“便宜”。它只不过把账单推到了以后，推给了别人。
不只是个案 - 有数据为证

第二部分
而这不只是一个个案。一项大规模的代码改动分析 - 超过六亿次改动 - 发现重复代码块增加了百分之八十一，而重构和复用的代码在全部改动中的占比则从百分之二十一骤降到不足百分之四。Google 自己的 DORA 研究发现，AI 使用的增加，伴随着交付稳定性可衡量的下降。那一个团队故事里的模式，正在整体数据中显现出来。
为何重要 - 说精确点
代价一

Tokens

让 agent 去重新推导本已存在的东西，会实打实地消耗算力 - 每个团队、每个冲刺都在烧。而且会不断累积。

代价二

正确性

原来的组件赢得了多年的打磨。而复制出来的那份则从零开始 - 不管它看起来多有把握。

写起来便宜，养起来昂贵。

第二部分
我们来精确地说清楚，为什么那个决定仍然是个问题，因为“这在技术上不够高效”打动不了任何人。有两项具体的代价。 第一：token。每当一个 agent 重造某样东西、而不是去找到它，它就在实打实地烧算力，从零开始把公司早已解决的问题重新推演一遍 - 在每个团队、每项任务上都是如此。这会一个冲刺接一个冲刺地累积。 第二：正确性。原来的组件不只是能编译 - 它赢得了多年的打磨。每一个边界情况、每一个安全补丁、每一次让人从中学到教训的故障。这些一样都不会传递给复制品。无论第一天看起来多有把握，副本都是从零开始。总得有人为它打补丁、做安全加固，年复一年 - 重新赢得原件早已付过一次代价的正确性。 这正是那个陷阱：写起来便宜，养起来昂贵，而账单会在所有人都不再关注之后才送到。

第二部分
所以，如果说重复的诱惑可以理解，那么诚实的问题是：评审这条路一开始为什么就这么重？核心就在这里，而且在我调研过的社区里几乎是普遍现象：提交一份贡献的成本已经降到接近于零，而评审一份贡献的成本却纹丝未动。如今 AI 产出贡献的速度，已经快过任何组织能够评审它们的速度。一位受访者告诉我，有一个备受瞩目的内部项目彻底关停了 - 把源码封闭了起来 - 因为它招架不住 AI 生成的拉取请求的洪流。 这不只是内部的事。以 curl 为例 - 它是地球上使用最广泛的软件之一。到去年，提交给 curl 的安全报告中大约五分之一借助了 AI。在所有报告里，约二十分之一是真正的漏洞 - 而这些真实漏洞无一例外都来自人。六年间，AI 生成的报告中发现真实漏洞的数量是零。今年 1 月，curl 关停了它的漏洞赏金计划 - 尽管后来随着 AI 垃圾提交退潮又重新开放了。
真正的前沿

教会 agent 养成内源的习惯。

✓ 已在真实环境中落地

复用共享的那部分

一种共享规格（spec）的模式 - 由一个团队掌管需求，其他团队只读消费，就在 agent 读取它们的地方。

✓ 已在真实环境中落地

把新东西发布回去

Shell 的 Project Fleming - 由 AI 驱动的发现，能找到与你的需求仅仅相邻的代码。

□ 仍然一片空白

构建之前先搜索

让 agent 先去查找，再决定要不要重新推导。这正是摆在这个社区面前的机会，从今天开始。

来源：OpenSpec（共享规格模式）；Shell Project Fleming。
第二部分
而这才真正是前沿所在。不是去管理那股洪流 - 那是分诊、是修管道的活儿。真正的大奖，是教会 agent 本身养成内源的习惯：构建之前先查找，去拉取共享的那部分而不是重新推导它，而当你构建出真正新颖、可复用的东西时，把它推送回去。 我已经找到了真实、鲜活的例子，而且没有人把它叫做内源 - 一种共享规格的模式，由一个团队掌管需求，其他团队只读消费，就在他们的编码 agent 能读到的地方。还有 Shell 自己的 AI 驱动发现工具，能找到与你所要求的仅仅相邻的代码。 三条腿里的两条 - 复用，以及回馈发布 - 此刻已经在建了。第三条腿 - 真正会在构建之前先搜索的 agent - 仍然是一片空白。这不是一个需要焦虑的缺口。这是从今天起，摆在这个社区面前的机会。
带走两点
1

在 AI 时代，内源并没有过时。AI 让它要解决的问题变得更大、更快 - 而不是更小。

2

前沿在于教会 agent 养成内源的习惯：构建前先搜索、复用、回馈贡献。

未来走向
如果今天你只带走两点，就带走这两点。第一：在 AI 时代，内源并没有过时。AI 让内源所要解决的问题变得更大、更快，而不是更小。第二：下一个前沿不是去管理那股洪流 - 而是教会 AI agent 本身养成内源的习惯。构建前先搜索、复用、回馈贡献。

第二部分
我想给你们举一个真实的例子，来自我为准备这次演讲而交谈过的一家大型电商公司内部。一个团队需要某项能力。他们自己的 AI 工具找到了它 - 它早已存在，在公司别处构建好、正常运行着。而这个团队还是又重新造了一遍。那个人是这么说的：“回馈贡献的阻力感觉太大了。”于是他们干脆让 AI 从零起了一个副本。 关于这给组织带来的代价，他们自己的原话是：“如果治理没有随之提速，单纯的 AI 效率会在不经意间绕过并饿死协作循环。”接着，几乎像是随口一提，那句一直萦绕在我心头的话：“与社区并肩合作、参与其中的价值不再被认可，这在工作时间里几乎变得难以承受。”这是一个在乎这件事的人，眼看着它发生，并如实说了出来。 那么 - 一个值得静下心来想的问题。那个团队的决定真的错了吗？在当下、在那一天、在赶工期的情况下 - 大概没错。他们把东西交付了。而这正是让下一个观点真正击中人的地方。
