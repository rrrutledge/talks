PART 2

How AI is reshaping InnerSource

What I'm seeing across the community
Now to the second half - what I'm actually seeing as AI meets InnerSource in practice.
Name it directly
The myth

InnerSource existed because code was expensive. If AI makes code nearly free - doesn't that end the argument?

Why it doesn't hold

AI collapses the cost of code that compiles. Not the cost of code that's correct - secure, tested, hardened.

Make it cheap, you get more of it. Including duplication.

Part 2
Here's a story a lot of us are telling ourselves. InnerSource exists because writing code used to be expensive: if two teams need the same thing, it's cheaper for one to build it and the other to reuse it. Now AI writes code in seconds. So the myth goes: if creating code is basically free, why bother reusing anything? Doesn't AI quietly end the argument for InnerSource? Here's why that's wrong. AI collapses the cost of writing code that compiles and looks right. It does nothing about the cost of code that's actually correct - secure, tested against every edge case your organization already learned the hard way. And when you make something cheap, you get more of it. That includes duplication.
Not just anecdote - from the source
+81%

Rise in duplicated code blocks.

Reused / refactored code fell from 21% to 3.8% of changes. And DORA paired more AI use with a drop in delivery stability.

GitClear - The Maintainability Gap, 2026 (623M changes)

Part 2
This isn't one anecdote. An analysis of over six hundred million code changes found duplicated code blocks up eighty-one percent, while refactored and reused code collapsed from twenty-one percent to under four percent of all changes. Google's DORA research found increased AI usage paired with a measurable drop in delivery stability.
Why it matters - be precise
Cost 1

Tokens

An agent re-deriving what already exists burns real compute - on every team, every sprint. It compounds.

Cost 2

Correctness

The original earned years of hardening. The duplicate starts back at zero - however confident it looks.

Cheap to write. Expensive to own.

Part 2
Two concrete costs. First, tokens: every time an agent rebuilds something instead of finding it, it burns real compute re-solving a problem the company already solved - on every team, on every task. Second, correctness: the original component earned years of hardening - every edge case, every security patch, every outage that taught somebody something. None of that transfers to a duplicate. Cheap to write, expensive to own - and the bill arrives after everyone has stopped paying attention.

Part 2
There's a second strain, and it's almost universal across the practitioners I surveyed: the cost of producing a contribution has dropped to near zero, but the cost of reviewing one hasn't moved at all. One respondent described a high-profile internal project that closed its source entirely because it couldn't handle the flood of AI-generated pull requests. The open source world sees it too: curl, one of the most widely used pieces of software on Earth, shut down its bug bounty in January under a wave of AI-generated reports - across six years, not one AI-generated report found a real vulnerability.
The real frontier

Teach agents the InnerSource habit.

✓ Shipping in the wild

Reuse the shared piece

A shared-spec pattern - one team owns requirements, others consume read-only, right where the agent reads them.

✓ Shipping in the wild

Publish back what's new

Shell's Project Fleming - AI-powered discovery finding code that's merely adjacent to your ask.

□ Still wide open

Search before you build

Agents that look first, before re-deriving. The opportunity in front of this community, starting today.

Source: OpenSpec (shared-spec pattern); Shell Project Fleming.
Part 2
So that's the frontier. Not just managing the flood - the real prize is teaching agents themselves the InnerSource habit: look before you build, pull the shared piece instead of re-deriving it, and when you build something genuinely reusable, contribute it back. We're already seeing pieces of it, without anyone calling it InnerSource: teams publishing shared specs right where other teams' coding agents can read them, and AI-powered discovery tools that surface the code you didn't know existed. Reuse and publishing back are being built right now. The third leg - agents that reliably search before they build - is still wide open. For a community like this one, building the platforms that open source and AI run on, that's the opportunity in front of us.

What comes next
If you take two things from today, take these. First: InnerSource isn't obsolete in the AI era - AI makes the problem InnerSource solves bigger and faster, not smaller. Second: the next frontier is teaching AI agents the InnerSource habit - search before you build, reuse, and contribute back.
